InfoDeck — v1.5 · D2 design

Attaching the card's files to a share. The plumbing already exists — the FileProvider is declared and already carries the QR image — so this is mostly a picker, a choice between attach and bundle as .zip, and being honest about the two things that can bite: apps that drop your text, and masking that the attachment quietly undoes.

C1 · The two ways files travel

#ModeMechanismStrengthWeakness
1AttachOne file → ACTION_SEND + EXTRA_STREAM; several → ACTION_SEND_MULTIPLE, both through the existing FileProviderNative, one tap, files arrive as filesSome apps keep the attachment and drop the text
2BundleA .zip holding a .txt of the card plus every ticked file, sent as a single attachmentNothing can be separated or dropped; one item to forwardThe receiver has to unzip; no preview in chat
3DefaultAttach when one file is ticked, offer Bundle from two upwards; the choice is remembered per card Q2

C3 · Rules

#RuleDetail
1Per-file ticksEvery file is its own row with size and date; files start unticked Q3
2MIMETaken from the stored file — application/pdf, the DOCX type, and so on; a mixed selection sends as */*
3URIsAlways through the FileProvider with a read grant; the app's own paths are never exposed
4Missing fileDropped from the send, named in a message; the rest still goes
5SizeWarned above 25 MB before an app is chosen Q6
6ZipWritten to cache, deleted when the share returns; cancelling leaves nothing
7MaskingMasked field + ticked file → the warning in S2. Never blocked, never hidden
8Many cardsSelection-mode shares with files always bundle — a dozen loose attachments is not a share Q7
